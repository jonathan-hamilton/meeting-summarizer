# S3.6 State Management Redesign - Implementation Plan

## Overview
Centralize speaker and segment state management to eliminate synchronization issues and improve performance.

## Current State Analysis

### Problems Identified
1. **Multiple Sources of Truth:** `speakerSegments` state in TranscriptDisplay vs useSpeakerStore
2. **Complex Filtering Logic:** Repeated calculations in multiple components
3. **Performance Issues:** Multiple re-renders from inefficient memoization
4. **Synchronization Bugs:** Speaker persistence after reassignments
5. **Prop Drilling:** Complex prop passing for filtered data

### Current Architecture
```
TranscriptDisplay (State Owner)
├── speakerSegments (useState)
├── currentlyActiveSpeakers (useMemo)
├── filteredDetectedSpeakers (useMemo)
├── speakerMappingStats (useMemo)
└── SpeakerMapping
    └── effectiveData (useMemo with complex filtering)
```

## Target Architecture

### Centralized Store Structure
```typescript
interface SpeakerSessionState {
  // Base State (Single Source of Truth)
  transcriptionId: string | null;
  originalSegments: SpeakerSegment[];
  currentSegments: SpeakerSegment[];
  speakerMappings: SpeakerMapping[];
  
  // Derived State (Computed Selectors)
  activeSpeakers: string[];           // speakers with current segments
  speakerStats: SpeakerStats;        // counts, mapping status
  filteredMappings: SpeakerMapping[]; // only active speakers
  
  // Actions
  initializeSession(transcriptionId: string, segments: SpeakerSegment[]): void;
  reassignSegment(segmentIndex: number, newSpeaker: string): void;
  updateSpeakerMapping(speakerId: string, mapping: Partial<SpeakerMapping>): void;
  resetToOriginal(): void;
  clearSession(): void;
}
```
