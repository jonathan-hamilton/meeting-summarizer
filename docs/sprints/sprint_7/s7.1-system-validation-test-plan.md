# S7.1 System Validation Test Plan

## Overview

This document provides a comprehensive test plan for validating the complete CI/CD system including development and production pipelines, environment separation, blue-green deployment, and rollback procedures.

## **🎯 Test Objectives**

### Primary Objectives
1. Validate development pipeline automation and reliability
2. Verify production deployment process with approval gates
3. Test blue-green deployment and rollback mechanisms
4. Confirm environment separation and security configurations
5. Validate monitoring, alerting, and health check systems

### Success Criteria
- ✅ Development deployments complete successfully in < 10 minutes
- ✅ Production deployments complete with manual approval in < 20 minutes
- ✅ Blue-green deployment executes without user interruption
- ✅ Rollback procedures complete in < 5 minutes
- ✅ All health checks validate correctly
- ✅ Environment separation prevents cross-environment access

## **🧪 Test Cases**

## **Category 1: Development Pipeline Testing**

### Test Case 1.1: Automatic Development Deployment
**Objective**: Verify automatic deployment triggers on code push
**Prerequisites**: Clean development environment, valid GitHub configuration

**Test Steps**:
1. Create test branch: `git checkout -b test/dev-pipeline-1`
2. Make minor code change: Add comment to a file
3. Commit and push: `git commit -m "test: dev pipeline validation" && git push origin test/dev-pipeline-1`
4. Monitor GitHub Actions for automatic pipeline trigger
5. Wait for pipeline completion

**Expected Results**:
- Pipeline triggers automatically within 30 seconds
- Build and test steps complete successfully
- Infrastructure deployment succeeds
- Application deployment succeeds
- Smoke tests pass
- Development URL responds with 200 status
- Total deployment time < 10 minutes

**Validation Commands**:
```bash
# Check health endpoint
curl -f https://app-meetingsummary-dev.azurewebsites.net/health

# Check detailed health
curl -s https://app-meetingsummary-dev.azurewebsites.net/health/detailed | jq .

# Verify API endpoints
curl -o /dev/null -s -w "%{http_code}" https://app-meetingsummary-dev.azurewebsites.net/api/auth/status
```

### Test Case 1.2: Development Pipeline Failure Handling
**Objective**: Verify pipeline handles build/test failures correctly
**Prerequisites**: Development environment ready

**Test Steps**:
1. Create test branch: `git checkout -b test/dev-pipeline-failure`
2. Introduce compilation error (remove semicolon in C# file)
3. Commit and push changes
4. Monitor pipeline execution and failure handling

**Expected Results**:
- Pipeline detects build failure
- Deployment steps are skipped
- Previous working version remains deployed
- Notification sent about build failure
- Development environment remains accessible

### Test Case 1.3: Multiple Branch Deployment
**Objective**: Verify development environment handles multiple concurrent deployments
**Prerequisites**: Clean development environment

**Test Steps**:
1. Create two test branches simultaneously
2. Push changes to both branches within 1 minute
3. Monitor pipeline execution and concurrency handling

**Expected Results**:
- Second deployment cancels first (due to concurrency group)
- Latest deployment completes successfully
- Environment reflects latest changes
- No deployment conflicts occur

## **Category 2: Production Pipeline Testing**

### Test Case 2.1: Production Deployment with Approval
**Objective**: Verify complete production deployment process with manual approval
**Prerequisites**: Clean production environment, approval team available

**Test Steps**:
1. Ensure main branch has successful development deployment
2. Navigate to GitHub Actions → "Deploy to Production" workflow
3. Click "Run workflow" → Select "production" → Click "Run workflow"
4. Wait for approval gate to appear
5. Have authorized team member approve deployment
6. Monitor complete deployment process

**Expected Results**:
- Workflow waits at approval gate
- Approval gate displays pre-deployment checklist
- Authorized approver can approve deployment
- Build and test phase completes successfully
- Security scanning passes
- Staging slot deployment succeeds
- Health checks validate staging deployment
- Traffic switch to production completes
- 10-minute monitoring period passes
- Production URL serves new deployment

**Validation Commands**:
```bash
# Check production health
curl -f https://app-meetingsummary-prod.azurewebsites.net/health

# Check staging slot health (old version)
curl -f https://app-meetingsummary-prod-staging.azurewebsites.net/health

# Verify version deployment
curl -s https://app-meetingsummary-prod.azurewebsites.net/health/detailed | jq .version
```

### Test Case 2.2: Production Approval Rejection
**Objective**: Verify deployment stops when approval is rejected
**Prerequisites**: Production environment ready

**Test Steps**:
1. Initiate production deployment workflow
2. Wait for approval gate
3. Have authorized team member reject deployment
4. Verify deployment stops and does not proceed

**Expected Results**:
- Deployment stops at approval gate
- No further pipeline steps execute
- Production environment remains unchanged
- Rejection notification sent to relevant teams

### Test Case 2.3: Emergency Production Deployment
**Objective**: Verify emergency deployment bypasses approval
**Prerequisites**: Emergency authorization, production environment ready

**Test Steps**:
1. Run production workflow with emergency flags:
   - `skip-approval: true`
   - `skip-tests: false` (for safety)
2. Monitor accelerated deployment process

**Expected Results**:
- Approval gate is bypassed
- Emergency deployment warning displayed
- Deployment proceeds with enhanced monitoring
- Emergency notification sent to all teams
- Deployment completes successfully

## **Category 3: Blue-Green Deployment Testing**

### Test Case 3.1: Blue-Green Traffic Switch
**Objective**: Verify seamless traffic switching between production slots
**Prerequisites**: Production environment with staging slot

**Test Steps**:
1. Deploy version A to production
2. Verify production serves version A
3. Deploy version B to staging slot
4. Verify staging slot serves version B
5. Execute blue-green traffic switch
6. Verify production now serves version B
7. Verify staging slot now serves version A

**Expected Results**:
- Traffic switch completes in < 30 seconds
- No user-facing downtime occurs
- Production serves new version immediately after switch
- Staging slot contains previous version for rollback
- All health checks pass after switch

**Validation Commands**:
```bash
# Before switch
curl -s https://app-meetingsummary-prod.azurewebsites.net/health/detailed | jq .version
curl -s https://app-meetingsummary-prod-staging.azurewebsites.net/health/detailed | jq .version

# Execute switch via Azure CLI
az webapp deployment slot swap \
  --name app-meetingsummary-prod \
  --resource-group rg-meetingsummary-prod \
  --slot staging \
  --target-slot production

# After switch - versions should be swapped
curl -s https://app-meetingsummary-prod.azurewebsites.net/health/detailed | jq .version
curl -s https://app-meetingsummary-prod-staging.azurewebsites.net/health/detailed | jq .version
```

### Test Case 3.2: Health Check Failure Prevention
**Objective**: Verify deployment blocks traffic switch when health checks fail
**Prerequisites**: Ability to simulate health check failure

**Test Steps**:
1. Deploy intentionally broken version to staging slot
2. Attempt production deployment
3. Verify health checks detect failure
4. Verify traffic switch is prevented

**Expected Results**:
- Health checks detect staging slot failure
- Traffic switch is blocked
- Production continues serving working version
- Alert notifications sent about failed deployment
- Staging slot marked as unhealthy

## **Category 4: Rollback Procedure Testing**

### Test Case 4.1: Automatic Rollback Trigger
**Objective**: Verify automatic rollback on health check failure
**Prerequisites**: Production environment with working deployment

**Test Steps**:
1. Deploy working version to production
2. Deploy broken version that passes initial checks but fails after traffic switch
3. Wait for monitoring period to detect issues
4. Verify automatic rollback triggers

**Expected Results**:
- Monitoring detects health check failures
- Automatic rollback triggers within 5 minutes
- Traffic switches back to previous working version
- Production service restored
- Rollback notifications sent to teams

### Test Case 4.2: Manual Rollback via Script
**Objective**: Verify manual rollback script functionality
**Prerequisites**: Production environment with previous version in staging slot

**Test Steps**:
1. Navigate to project root directory
2. Execute rollback script:
   ```bash
   ./.github/scripts/rollback.sh \
     --app-service app-meetingsummary-prod \
     --type slot-swap \
     --yes
   ```
3. Monitor rollback execution and verification

**Expected Results**:
- Rollback script executes successfully
- Slot swap completes within 2 minutes
- Health checks validate rollback success
- Production serves previous working version
- Rollback report generated

### Test Case 4.3: Manual Rollback via Azure Portal
**Objective**: Verify manual rollback through Azure Portal
**Prerequisites**: Access to Azure Portal, production environment

**Test Steps**:
1. Open Azure Portal
2. Navigate to App Service: `app-meetingsummary-prod`
3. Go to "Deployment slots"
4. Click "Swap" between production and staging
5. Confirm and execute swap

**Expected Results**:
- Azure Portal shows slot swap options
- Swap operation completes successfully
- Traffic redirected to previous version
- Health checks confirm rollback success

### Test Case 4.4: Rollback Performance Validation
**Objective**: Verify rollback completes within SLA timeframes
**Prerequisites**: Production environment ready for rollback test

**Test Steps**:
1. Record current production version and timestamp
2. Execute rollback using fastest method (slot swap)
3. Measure time from rollback initiation to service restoration
4. Validate performance against SLA targets

**Expected Results**:
- Rollback completes in < 5 minutes (SLA target)
- Service downtime < 30 seconds
- All functionality restored after rollback
- Performance metrics meet baseline

## **Category 5: Security and Environment Separation Testing**

### Test Case 5.1: Environment Isolation
**Objective**: Verify complete isolation between development and production
**Prerequisites**: Both environments deployed

**Test Steps**:
1. Attempt to access production database from development environment
2. Verify development service principal cannot access production resources
3. Test network connectivity restrictions
4. Validate secret/configuration separation

**Expected Results**:
- Development environment cannot access production resources
- Network isolation prevents cross-environment communication
- Service principals have appropriate role restrictions
- Secrets are environment-specific and secure

**Validation Commands**:
```bash
# Verify resource group isolation
az resource list --resource-group rg-meetingsummary-dev
az resource list --resource-group rg-meetingsummary-prod

# Test database connectivity restrictions
# (should fail from wrong environment)
```

### Test Case 5.2: OIDC Authentication Security
**Objective**: Verify GitHub OIDC authentication works securely
**Prerequisites**: GitHub environments configured with OIDC

**Test Steps**:
1. Monitor GitHub Actions logs for OIDC token exchange
2. Verify no long-lived secrets stored in GitHub
3. Validate federated credentials work only for correct environments
4. Test token expiration and renewal

**Expected Results**:
- OIDC authentication succeeds for correct environments
- No secrets visible in GitHub Actions logs
- Federated credentials restricted to appropriate subjects
- Tokens automatically expire and renew

### Test Case 5.3: Secret Management Security
**Objective**: Verify secrets are managed securely across environments
**Prerequisites**: Azure Key Vault and GitHub secrets configured

**Test Steps**:
1. Verify Azure Key Vault access policies
2. Test application secret retrieval
3. Validate secret rotation capabilities
4. Check audit logging for secret access

**Expected Results**:
- Only authorized identities can access Key Vault
- Applications retrieve secrets successfully
- Secret access is logged and auditable
- Rotation procedures work correctly

## **📋 Final Validation Criteria**

### System Ready for Production Use When:
- ✅ All critical test cases pass (Categories 1-6)
- ✅ Performance metrics meet or exceed targets
- ✅ Security validation complete with no high-risk findings
- ✅ Documentation validated and team trained
- ✅ Incident response procedures tested and verified
- ✅ Rollback procedures validated under 5-minute target
- ✅ Blue-green deployment tested with zero downtime
- ✅ Environment separation confirmed secure

### Acceptable Risk Items:
- ⚠️ Non-critical documentation gaps (with remediation plan)
- ⚠️ Performance slightly below target in development (acceptable)
- ⚠️ Minor operational procedure improvements needed

### Go/No-Go Decision Criteria:
- 🔴 **NO-GO**: Any critical security issues
- 🔴 **NO-GO**: Production deployment or rollback failures
- 🔴 **NO-GO**: Environment separation breaches
- 🟢 **GO**: All critical functions working, minor issues documented
