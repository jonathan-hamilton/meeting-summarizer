# S6.5 Implementation Plan: Persistent Upload Progress & Meeting History

## Story Overview
**S6.5**: As a paid user, I want my upload progress and meeting history to persist across browser refreshes and sessions so that I can resume work and access past meetings.

**Dependencies**: S6.1 (Azure Storage), S6.4 (Transcript Storage Optimization)

### Phase 3: Search & Advanced Features

## Technical Architecture

### Database Schema
```sql
CREATE TABLE MeetingHistory (
    Id uniqueidentifier PRIMARY KEY DEFAULT NEWID(),
    UserId uniqueidentifier NOT NULL FOREIGN KEY REFERENCES Users(Id),
    BatchJobId uniqueidentifier NULL FOREIGN KEY REFERENCES BatchTranscriptionJobs(Id),
    TranscriptBlobUrl nvarchar(500) NULL,
    FileName nvarchar(255) NOT NULL,
    Title nvarchar(255) NULL,
    ProcessingStatus nvarchar(50) NOT NULL,
    Duration int NULL,
    ProcessingTimeMs bigint NULL,
    SpeakerCount int NULL,
    FileSize bigint NULL,
    ConfidenceScore float NULL,
    Participants nvarchar(1000) NULL,
    UploadedAt datetime2 NOT NULL DEFAULT GETDATE(),
    CompletedAt datetime2 NULL,
    ExpiresAt datetime2 NOT NULL DEFAULT DATEADD(year, 1, GETDATE()),
    INDEX IX_MeetingHistory_UserId_CreatedAt (UserId, UploadedAt DESC)
);
```

### Real-time Updates Architecture
- **SignalR Hub**: MeetingProgressHub for instant status synchronization
- **Cross-device Sync**: Status updates across all user sessions
- **Integration**: BatchTranscriptionJobService updates MeetingHistory on status changes

### Frontend State Management
- **Zustand Store**: Centralized meeting history state management
- **Real-time Updates**: SignalR client integration
- **Navigation**: New /history route with header navigation
